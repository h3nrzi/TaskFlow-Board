# Frontend-facing domain and contract requirements

Decision owner: [Define the frontend-facing contract needed for incremental API integration](../issues/03-api-contract.md).

Status: approved on 2026-10-24. Q27 explicitly confirmed this complete specification against the approved Q1–Q26 decisions and all ten review scenarios, with no material discrepancies, and authorized resolution of the owning decision. This document specifies requirements; it is not a production contracts package or an implementation acceptance record.

## Contract authority and progressive integration

One shared monorepo contracts package owns API DTOs, common enums, request/response schemas, error contracts and account/profile contracts. Runtime schemas are authoritative; TypeScript types are inferred. UI state, browser snapshots and business logic stay outside the package. Connected operations act on resources/domain operations rather than upload a whole browser workspace snapshot. Q2's proposed separate frontend/backend API contracts were rejected.

Apply [Choose shared-schema and OpenAPI tooling](../issues/10-contract-tooling.md#answer) and its linked design: browser-safe Zod 4 schemas, Nest-side nestjs-zod, strict requests, tolerant additional response fields with declared fields validated, distinct input/output schemas as necessary, and catalog-driven OpenAPI 3.1 with the mandatory generation safeguards. Shared wire schemas do not implicitly transform, coerce or default values. No package versions or production package are created here.

Retain one logical workspace and deliberate module-by-module activation. Each coupled domain has one authority for reads/writes. Project deletion and task cascade cannot span independent authorities. Real authentication/profile may connect while tasks/projects remain local; theme remains local. Local snapshot saves must not independently persist or overwrite connected profile authority. A connected failure never silently falls back to browser storage or demo authentication.

## Resources, IDs and fields

Connected resource IDs are generated by NestJS and treated as opaque strings by the frontend. IDs and audit timestamps are server-owned and not client-editable. This does not choose an ID-generation algorithm or an identifier syntax. Account identity is immutable; display name and account email do not define that identity.

Task editable fields are title, description, status, priority, projectId, dueDate and assignee. Project editable fields are name, description, color and icon. Do not impose one resource's fields on another.

| Concern | Approved requirement |
| --- | --- |
| Task status | todo, in-progress, done; any transition among them is allowed |
| Task priority | low, medium, high, urgent |
| Standalone task | projectId: null |
| Assigned task | projectId references a project accessible in the authenticated account's private workspace |
| Due date | Calendar-date string YYYY-MM-DD, or null when absent; no timezone conversion |
| Assignee | Optional free-text label, distinct from account identity; null when absent |
| Description | String; empty is ""; preserve whitespace and line breaks exactly |
| Creation/update metadata | Applicable server-controlled timestamp instants, canonical UTC ISO 8601 strings with milliseconds; display in the viewer's local timezone |
| Titles/names | Nonblank; duplicate task titles and project names are permitted |
| Account presentation | Expose account ID, email and editable display name; derive avatar initials from display name |

This does not add new metadata fields to resources or select an avatar-initials algorithm. Concrete DTO inventory and color/icon constraints belong to [Specify the shared Schema-First contracts](../issues/13-shared-schema-contracts.md).

## Create, update and result semantics

Task creation requires all seven fields: title, description, status, priority, projectId, dueDate and assignee. Project creation requires all four fields: name, description, color and icon. All are explicitly present, including empty descriptions and nullable values. Frontend forms may supply default choices; the backend must reject missing required create fields rather than silently fill them.

Updates are partial: omitted fields remain unchanged. Explicit null clears only supported nullable fields: task project assignment, due date and assignee. Empty description is cleared text, not null. IDs and audit timestamps cannot be edited. Request unknown-field rejection follows the approved tooling policy, including nested objects where applicable.

Create/update returns authoritative resource values, including normalized text and server-owned metadata. Missing updates return not-found. This does not specify a response envelope or select patch/HTTP mechanics.

### Normalization and lengths

Trim task titles, project names, account display names and non-null assignee labels before authoritative validation/storage. Required titles/names/display names must contain non-whitespace text; non-null blank assignee strings are rejected, with null used for clearing. Return authoritative normalized values.

| Field | Maximum Unicode code points |
| --- | ---: |
| Task title | 200 |
| Project name | 120 |
| Account display name | 100 |
| Free-text assignee | 120 |
| Task/project description | 10,000 |

Evaluate applicable name/label length and nonblank constraints against the normalized value. Evaluate description length against its preserved content. NestJS must enforce canonicalization/validation independently of frontend behavior. Normalization stays outside shared wire schemas; neither request nor response schemas silently transform values.

[Assign validation ownership across forms, domain rules and external data](../issues/05-validation-ownership.md) and the shared-schema decision must specify how boundary validation and canonicalization compose so that raw surrounding whitespace does not incorrectly fail a normalized-value limit. They may not silently move the approved length rule to the unnormalized value. Unicode code points must not be confused with UTF-16 code units, bytes or user-perceived grapheme clusters.

## Private workspace reads and deletion

Projects/tasks belong to the authenticated account's private workspace. Enforce ownership on every read, update, delete and relational reference. Defer collaboration; free-text assignment does not grant another account access.

For the MVP, return complete account-scoped project/task collections, without pagination or silent truncation. Empty collections are successful results. Filtering and presentation sorting remain frontend-side initially. Each returned task references an accessible project or has projectId: null. Revisit pagination only when actual scale or product requirements justify it. This does not promise a transactionally consistent snapshot across separate requests; the architecture decision owns consistency requirements made necessary by concrete workflows.

Project deletion includes its task cascade as one consistent backend-owned operation under the same account scope. All related deletion effects must respect ownership.

Authenticated deletion of a well-formed ID that is absent or belongs to another account returns an indistinguishable successful confirmed-absence outcome. Foreign resources and their tasks must never be modified. Reads/updates of foreign resources return concealed not-found. Authentication failures, malformed requests and genuine service failures remain explicit errors. Q26 qualifies Q19's general not-found concealment rule specifically for deletion while preserving Q15's absent-deletion semantics. Exact successful deletion response belongs to the Endpoint Catalog.

## Account, profile and authentication-facing guarantees

Successful authentication establishes the current account's opaque ID, email and display name. The current demo profile is not authenticated identity. Distinguish no authenticated session from a failed/unavailable session-status request. Profile updates return authoritative presentation data. Sign-out reports confirmed completion or explicit failure; it never silently reverts to demo authentication or pretends a remote operation succeeded.

Account email changes are a separate security-sensitive operation, not an unrestricted profile update. [Define account email-change scope and security requirements](../issues/16-account-email-change.md) must settle inclusion/deferral and applicable verification/authorization/completion requirements before the Endpoint Catalog. No email-change endpoint is approved by this specification alone.

Authentication technology, credentials/session transport and backend authentication implementation are not selected here. Authentication-facing API design needed for the MVP remains with the blueprint/catalog; presentation of pending operations and failures belongs to the async decision. No implementation acceptance is inferred from these requirements.

## Errors and compatibility

Errors carry stable machine-readable codes, safe user-displayable messages and field paths for validation failures. Distinguish unauthenticated requests, authorization failures, validation failures, missing resources and service failures, subject to resource-existence concealment above. Do not expose stack traces or sensitive implementation details. Concrete codes, field-path encoding, HTTP statuses and response encoding belong to the Endpoint Catalog and shared-schema specification.

Check both consumers and potentially different deployed frontend/backend versions. Treat required request additions, response field removal/change and enum expansion as changes needing explicit compatibility review and coordinated handling. Additional response fields remain tolerated/stripped under the approved response-reader policy; missing/invalid declared fields remain errors. No speculative API-versioning infrastructure is selected.

## Retained behavior, revisions and deferred owners

This is documentation/contract design only. Browser-local code/storage and current forms remain unchanged. Preserve local independence, standalone tasks, free-text assignment, project deletion cascade and existing local safeguards. The planned connected API intentionally revises local empty-string project assignment to null, date-only creation/update metadata to timestamp instants, permissive identity editing to account/profile separation, and missing-update behavior to explicit not-found. No development-data migration is required.

Minimum preparation is defined by requirements, not a mandatory preliminary refactor. Before activating an integration, operations must use its approved authority, validate external boundaries and isolate connected data from independent local snapshot persistence. No repository, cache, optimistic-update policy, synchronization system, ORM or database is selected.

## Review and evaluation guide

The user reviewed these scenarios against the approved decisions and confirmed shared understanding in Q27. For future implementation evaluation, reproduce each scenario below and record observations against its expected behavior. Scenario expectations are design requirements, not executed API tests. The next planning action is to resume [Define asynchronous operation completion and user feedback](../issues/04-async-operations.md).

1. **Create completeness:** a task includes all seven task fields, description: "", and projectId/dueDate/assignee: null where absent. Omitting status fails; adding project-only color fails under strict request validation. A project instead supplies its four project fields. Server-owned IDs/timestamps cannot be edited.
2. **Partial update:** omitting dueDate preserves it; dueDate: null clears it. Assignee: "   " fails after normalization; assignee: null clears it. A returned resource contains authoritative normalized text.
3. **Text boundaries:** surround a valid title with whitespace: evaluate nonblank/length after trimming. A 200-code-point title is within the limit; 201 is beyond it. Repeated supplementary-plane characters must count as code points rather than UTF-16 units. Description leading spaces/newlines remain exact; 10,001 code points is beyond its limit.
4. **Domain rules:** duplicate names/titles and done-to-todo transitions are allowed. A standalone task is valid. A foreign or missing project assignment cannot establish a relation; enforcement must not reveal another account's resource existence.
5. **Dates:** a due date remains the same calendar day across timezones. UTC millisecond creation/update timestamps display in the viewer's local timezone and cannot be edited.
6. **Deletion privacy/cascade:** compare deletion of missing, foreign and owned IDs. Missing/foreign well-formed IDs receive indistinguishable successful absence; foreign data stays unchanged. An owned project and its task cascade share one consistent account-scoped operation. Malformed IDs, unauthenticated requests and genuine service failures remain errors.
7. **Reads:** empty collections succeed; nonempty results are complete and account-scoped. Returned references are accessible or null. No silent truncation or failure-triggered demo initialization occurs.
8. **Account/auth:** identity survives display-name changes; avatar initials follow display name. Email is excluded from ordinary profile edits. Session-status failure differs from unauthenticated state. Sign-out failure is explicit, with no silent demo fallback. Remote profile and local tasks/theme preserve their separate authorities.
9. **Errors/evolution:** validation errors identify fields safely; internal stacks never reach the user. Additional response fields are tolerated, invalid required fields fail, and enum expansion triggers compatibility review.
10. **Ownership review:** follow the deferred-owner links and confirm that email security, exact schemas/HTTP and async behavior remain their own decisions. No new runtime/package changes are claimed.

Preflight and documentation checks are recorded in the owning ticket. Human evaluation/acceptance of any future implemented integration remains pending user observations, independently of design approval and automated checks.
