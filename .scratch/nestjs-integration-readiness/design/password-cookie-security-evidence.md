## Password policy and storage

**NIST normative requirements/recommendations:** Final SP 800-63B-4 §3.1.1.2 requires at least 15 characters for single-factor passwords, full verification without truncation, Unicode code-point length counting, whole-password blocklist checks and failed-attempt rate limiting. It prohibits composition rules and routine periodic password changes, and requires change after compromise evidence. It recommends accepting at least 64 characters maximum, printable ASCII/spaces and Unicode, with NFC normalization before hashing. It requires password-manager/autofill support and recommends paste. Passwords must travel through an authenticated protected channel and be salted/hashed with an appropriate cost-bearing scheme; costs should rise as practical. Store salt/hash plus algorithm/cost migration metadata. These requirements concern centrally verified passwords, not local PINs. [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver).

**OWASP recommendation:** Use modern slow password hashing with unique salts; plain text, reversible encryption and fast general-purpose hashing are unsuitable. Its leading option is Argon2id; an example minimum is 19 MiB, two iterations, parallelism one. Alternatives and FIPS constraints differ. Benchmark costs under expected load and support work-factor upgrades. Legacy bcrypt's 72-byte limit is incompatible with silently accepting arbitrary long Unicode passwords. A pepper, if used, needs separate secret management. This is algorithm evidence, not selection of a package or algorithm for TaskFlow. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

**Catalog choices remaining:** exact maximum (at least 64 is the recommendation), Unicode/NFC pipeline and when length/blocklist checks occur, prohibited control characters/ill-formed input handling, raw request byte bound, no silent whitespace/case changes, blocklist failure behavior, and storage capability requirements. Define enrollment and sign-in identically. Exact numeric abuse budgets and backoff are TaskFlow policy choices; a general guideline is not a measured safe operating limit for this service. Preserve generic public authentication errors without hiding a verified owner's useful password-policy rejection during restricted enrollment.

## Protected cookie and browser-origin constraints

**Browser behavior:** Omitting `Domain` creates a host-only cookie. A supported `__Host-` prefix requires HTTPS, `Secure`, `Path=/`, and no `Domain`; add `HttpOnly` explicitly. `HttpOnly` prevents script reading but still permits script-initiated cookie-bearing requests. `Secure` governs transport. Cookie paths are not security boundaries. `SameSite` concerns sites rather than full origins; `Lax` permits qualifying top-level safe navigation, while `None` requires `Secure`. Explicit settings avoid browser-default variations. Browser restoration can preserve session cookies. [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).

**Fetch standard:** Credentialed cross-origin fetch needs client credential inclusion, an explicit allowed origin and `Access-Control-Allow-Credentials: true`; wildcard origin cannot share a credentialed response. Preflights exclude credentials. Allowed methods/request headers must cover the actual contract, and nonsafelisted response headers need exposure. Dynamic origin responses need correct `Vary` behavior. A blocked CORS response does not establish that no server work occurred. [WHATWG Fetch, CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol).

**Implications:** A proposed `__Host-...; HttpOnly; Secure; Path=/; SameSite=Lax` contract is compatible with host-only authority but needs human approval and HTTPS-capable development evaluation. `/api` does not imply cookie `Path=/api` when using `__Host-`. A same-origin browser contract reduces CORS decisions; it does not settle production deployment. Same-site sibling origins remain distinct trust boundaries. Cross-site deployment requires renewed cookie/browser-policy evaluation. Server expiry and revocation remain authoritative regardless of cookie survival or deletion.

## CSRF, bootstrap and rotation

**OWASP recommendation:** Synchronizer tokens are secret, unpredictable and session-bound; bootstrap via HTML/JSON, submit in a custom header, validate server-side, and exclude tokens from URLs/logs. Per-request tokens can impair back navigation; per-session tokens reduce that friction. Login is CSRF-sensitive: use a pre-session token, then destroy the pre-session and create a new authenticated session rather than promote it. SameSite is defense in depth. Origin/Referer checking must match trusted full origins; missing/null origin is not proof of legitimacy. A mandatory custom-header/preflight defense is another option only with restrictive CORS; permissive origin allowlists defeat it. [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

**Proposed design to discuss, not approved:** a bootstrap response returns only a CSRF token and establishes a bounded anonymous context; token proof is required for registration/resend/sign-in and every protected mutation, including sign-out/activity touch. Verification/enrollment must specify equivalent request-integrity proof rather than gain exemptions by being “public.” Rotate context and token when crossing anonymous, restricted enrollment and authenticated authority boundaries. After sign-out/expiry, reject old tokens. Bootstrap itself must not verify email, enroll, sign in or refresh authenticated activity. Define multi-tab rebootstrap after rotation, stale-token error handling, Origin checks and no silent business-command retry. Keep credential and CSRF-token purposes separate.

## Restricted verification/enrollment credentials and sensitive responses

**Relevant OWASP analogy, not new recovery scope:** Its password-reset guidance recommends cryptographically random, sufficiently long, securely stored, single-use, expiring proof; generic request responses and throttling; HTTPS links with trusted URL construction; `Referrer-Policy: no-referrer`; and optional exchange into a restricted session. Those transport/leakage principles can inform enrollment while its password-reset workflow remains out of scope. [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

**Implications to decide:** landing-page GET must be scanner/prefetch-safe; consume proof only after intentional protected submission. Compare an in-memory bearer credential submitted in a POST body against exchange for a separate protected restricted cookie with server-enforced purpose and CSRF binding. Neither may authorize Workspace access or automatic sign-in. URL fragments reduce direct HTTP URL exposure but remain script/history-sensitive; query tokens require particularly careful redaction. Avoid third-party resources/analytics on credential landing pages, remove displayed credentials from browser location when feasible, redact URL/body/header logging, and never persist reusable credentials in localStorage. Specify `Cache-Control: no-store` for bootstrap, session/auth/profile/Workspace and credential-bearing responses as explicit TaskFlow sensitive-data policy; ensure errors never echo secrets. Exact credential entropy, lifetimes, resend invalidation, atomic consumption and account binding remain catalog decisions or retained earlier approvals.

## DELETE preconditions and safe recovery

**HTTP standard:** RFC 9110 §9.3.5 warns that DELETE request content lacks general semantics and may be rejected by intermediaries/servers; origin-specific support is insufficient to assume interoperability. Successful enacted deletion can return 204 without content or 200 with a status representation; 202 denotes incomplete action. `If-Match` uses strong entity-tag comparison; a missing representation makes its condition false. Failed conditions prevent application, generally with 412; already-applied changes can permit 2xx. DELETE's idempotent effect does not promise identical response bytes. [RFC 9110 §§9.3.5, 13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.5).

**Implication:** prefer a documented custom revision header over DELETE JSON content if retaining current TaskFlow revision/error/privacy semantics. Standard `If-Match` requires deliberate ETag representation semantics, wildcard/list rules and privacy-safe absent-resource handling; it is not merely another spelling of `expectedRevision`. A project deletion token sensitive to member changes may be a different domain precondition from the project's presentation revision. These remain user decisions. Test through the actual browser and ingress stack later.

**Current work in progress:** draft-ietf-httpapi-idempotency-key-header-08, published 2026-10-22 and expiring 2027-04-25, is an Internet-Draft, not a final standard. It describes a quoted Structured Field string, unique keys, published expiry and payload equivalence, with suggested 400 missing key, 422 changed payload and 409 concurrent request. Its revised retry text calls for a response consistent with completed user intent; exact original-result replay is no longer its earlier wording. Its security guidance recommends validated formats and client-scoped composite lookup keys. [IETF draft -08](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-08.html).

**TaskFlow product choices already supplied by the catalog owner:** account/operation scope, original validated-input equivalence, seven-day complete outcome retention, immutable original replay, and permanent minimal consumed-key markers after full outcome expiry with gap-free cleanup. These are stronger explicit TaskFlow guarantees, not consequences of the draft. Never turn an expired/missing outcome into permission to create; recovery authenticates and authorizes every time, cannot recreate a deleted resource or replace later values, and must distinguish historical outcome from current resource state. Permanent markers prevent reuse of known consumed keys but cannot prove absence after lost/corrupt evidence; service failure remains distinct from a genuinely first use.
