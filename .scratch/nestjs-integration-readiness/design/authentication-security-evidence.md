# Authentication security evidence for the API Architecture Blueprint

Research completed: 2026-10-24. Evidence only; no product approval or implementation. Owner: [Research mechanism-independent authentication security guarantees](../issues/17-authentication-security-evidence.md). Human decisions remain with [Define the API Architecture Blueprint for progressive integration](../issues/11-api-architecture-blueprint.md); email-change scope remains with its separate owner.

## Reading these findings

The sources below are current official OWASP guidance and final NIST SP 800-63B-4, not the superseded 63-3 edition or a draft. OWASP recommendations inform this private-workspace design. NIST addresses government digital identity assurance: its normative requirements are useful evidence, but this research does not declare TaskFlow compliant, select an assurance level, or import every NIST requirement into the MVP.

## Mechanism-independent baseline candidates

- **Trust and account scope:** Authentication establishes identity; authorization separately determines allowed actions. OWASP recommends deny-by-default behavior and permission checks on every request. Applied here, validated authentication establishes server-derived Account context; client account IDs, editable email/display name, free-text assignee and demo profile cannot establish authority. Workspace operations still enforce ownership and relationships. This application is consistent with the approved validation policy, not a newly selected middleware architecture. [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)
- **Transport and safe responses:** Secure API endpoints require HTTPS to protect confidentiality, integrity and server authentication. Keep credentials/tokens out of URLs. Return safe errors without stack traces or internal details. An internal failure must not become a successful authenticated state. [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#https)
- **Session lifecycle:** OWASP calls for server-enforced idle and absolute timeouts, renewal of session identity after authentication/privilege changes, and server-side invalidation on expiry and logout. Deleting browser state alone cannot invalidate a stolen copy; browser closure is not reliable logout. Its suggested timeout ranges are examples, not approved TaskFlow durations. Product policy must define which session(s) logout invalidates and when that invalidation becomes effective. These guarantees constrain later mechanism selection; they do not imply a particular session store. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#session-expiration)
- **Authentication freshness:** NIST distinguishes inactivity and overall lifetime limits; session activity resets inactivity, while successful reauthentication resets both. Access/refresh tokens can outlive an authentication session, so token validity alone does not establish current human presence. A long-lived renewal path must not silently erase the promised reauthentication boundary. Exact durations and persistence across browser restart require product decisions. [NIST SP 800-63B-4, sections 5.1–5.2](https://pages.nist.gov/800-63-4/sp800-63b.html#session)
- **Enumeration and abuse:** OWASP advises equivalent authentication failure messages for nonexistent, incorrect and unavailable accounts, accounting for status codes and timing as well as text. Registration can also expose account existence; generic failure wording alone does not hide a distinguishable successful registration. Throttling should consider account targeting rather than IP alone, while avoiding attacker-triggered denial of service through lockout. Exact policies and registration behavior need explicit decisions; no CAPTCHA or MFA selection follows from this evidence. [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-and-error-messages)
- **Secret exposure and audit:** Record authentication/access/session security events for investigation, but exclude or appropriately transform raw passwords, access tokens and session identifiers. Apply that policy to request/response logging as well as application messages. A safe operational diagnostic must not expose reusable credentials. [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#data-to-exclude)

## Controls conditional on the eventual browser mechanism

- **Automatically attached credentials:** Protect state-changing requests against CSRF. OWASP describes server-validated token patterns, explicit custom-header approaches and Fetch Metadata/origin validation with deliberate fallback behavior. SameSite is generally defense in depth, and GET must not perform state changes. Login/logout and other session transitions require review as well as Workspace mutations. Choose protections after the credential transport and browser origins are known. [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- **Session cookies, if selected:** Use secure transport, minimal host/path scope and appropriate HttpOnly/SameSite settings. Cookie expiry is not authoritative server expiry. **Script-accessible secrets, if considered:** NIST warns against insecure locations such as localStorage because XSS can expose them. These facts require an exposure analysis rather than selecting cookies, bearer tokens or a browser store here. [NIST SP 800-63B-4, session bindings and browser cookies](https://pages.nist.gov/800-63-4/sp800-63b.html#session-bindings)
- **Cross-origin API access, if needed:** Restrict CORS to intended origins and methods. CORS does not establish authenticated identity or replace access control. Exact origin configuration depends on later deployment decisions. [OWASP REST Security, CORS](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#cors)

## Email ownership and registration decision

Format validation and canonical comparison do not prove mailbox control. OWASP's email guidance recommends verifying ownership before enabling account use, with random, single-use, expiring verification tokens. It also cautions that local-part comparison policy must be explicit: provider-specific equivalence is not universal. This is an important recommendation to present to the human, not authorization to add verification to TaskFlow. [OWASP Email Validation and Verification](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html#email-ownership-verification)

**Design implication/inference:** The blueprint must ask whether registration grants immediate private-workspace access or waits for verified mailbox control. If verification is deferred, it must explicitly avoid treating the supplied email as proven ownership or authority for recovery, account linking or takeover-sensitive changes; record the accepted registration/identifier-squatting and enumeration trade-offs. If verification is approved, delivery, expiry, resend abuse and pending-account behavior become concrete design questions. Neither path selects a credential strategy. Password recovery remains outside this MVP; email-change policy retains its separate owner.

## Questions the blueprint must settle with the user

1. Idle/overall expiration guarantees, persistence expectations, reauthentication triggers, and which activity can extend which limit.
2. Current-session versus all-session sign-out, revocation effectiveness, treatment of requests already admitted, and unknown logout outcomes. Immediate revocation must not be promised if the later mechanism only stops future renewals.
3. Registration result and mailbox-ownership policy, including the observable account-existence trade-off.
4. Abuse-resistance and safe-error guarantees without locking out legitimate users indefinitely, especially while recovery is out of scope.
5. Which security outcomes must hold before each connected capability activates; exact HTTP/error/schema design remains with catalog and contract owners.

Preserve the approved [asynchronous operation policy](async-operation-policy.md): confirmed sign-out only, explicit uncertain outcomes, same-account draft retention on expiry, no automatic replay, and prior-account late-result isolation. A timeout or logout does not prove a dispatched domain mutation rolled back.

### Malicious preregistration and activation binding

Primary research by Sudhodanan and Paverd demonstrates that an attacker can preregister a victim's address and retain access after the victim takes control through surviving sessions, extra identifiers or outstanding capabilities. The authors' MSRC account describes these attacks and recommends verification before account use plus careful treatment of preexisting access. The issue is control of an authentication path, not merely whether an email field has become verified. [MSRC: Pre-hijacking attacks](https://www.microsoft.com/en-us/msrc/blog/2022/05/pre-hijacking-attacks), [original USENIX paper and authors](https://www.usenix.org/conference/usenixsecurity22/presentation/sudhodanan)

**Mechanism-independent implication/inference:** When a mailbox owner confirms an unsolicited preregistration, activation must not silently bless a credential, pending browser context or capability controlled by the original untrusted registrant. The owner needs a trustworthy binding to the eventual authentication path: either proof that the path being activated belongs to the verifying owner or safe re-establishment that removes the untrusted path. Previously issued pending tokens/contexts must not gain protected authority merely by observing that activation happened. Requesting resend or knowing the email is not that proof. This invariant constrains the eventual flow without selecting a password, passkey, token, provider or credential-setting sequence. It also does not imply recovery or global logout for established accounts.

### Automated email retrieval and intentional verification

RFC 9110 defines GET/HEAD as safe methods so automated retrieval and prefetching cannot trigger requested state changes; action-bearing URLs must not perform unsafe actions through safe methods. Auth0's first-party documentation specifically reports accidental email verification by scanners. These are evidence of the hazard, not a provider recommendation. [RFC 9110 §9.2.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1), [Auth0: Verify Emails](https://auth0.com/docs/manage-users/user-accounts/verify-emails)

**Implication/inference:** A verification landing GET/HEAD must not activate the account, consume the proof or create authenticated authority. An intentional confirmation action can perform the transition with appropriate request protections. POST alone is not proof of a human or mailbox owner: automatically submitting a form on page load recreates the problem. The chosen design must also prevent verification-proof leakage through referrers, logging and unrelated page resources. The earlier logging and browser-control evidence still applies.

### Resend, multiple proofs and delivery uncertainty

OWASP's email guidance requires expiring single-use verification proofs but does not prescribe one universal maximum number of outstanding links. Its OTP guidance recommends generating a new OTP and replacing the old record on resend; this is specific OTP guidance, not a universal rule for every verification-link design. [OWASP Email Verification](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html#email-ownership-verification), [OWASP MFA: OTP handling](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#one-time-password-otp-handling-and-storage)

**Trade-offs/inferences for decision:** Invalidating older proofs on every resend limits outstanding capabilities, but unauthenticated resends can repeatedly invalidate an owner's usable mail, and delayed delivery may present an obsolete link last. Allowing bounded overlapping proofs avoids that failure but increases outstanding capabilities. Either design needs atomic replay/activation handling, a definition of what successful activation invalidates, and protection against resends replacing owner-bound credentials or registration context. Single-use per token does not by itself settle the account-wide transition. No policy or numeric limit is selected here.

SMTP acceptance transfers responsibility to deliver or report failure; later delivery failures remain possible. A timeout around acceptance can also result in duplicates. Therefore an API's acceptance/scheduling confirmation is not proof that the person received the message. Pending accounts must not be activated by delivery acknowledgement or a resend request. Separate operational delivery failure from safe user-facing recovery without claiming delivery certainty. [RFC 5321 §§4.5.3.2.6, 6.1](https://datatracker.ietf.org/doc/html/rfc5321#section-6.1)

OWASP recommends consistent responses, timing and abuse protections for account-sensitive email flows. Applied to public registration/resend, generic behavior must cover nonexistent, pending, active and throttled-per-account states; branch-specific delivery errors, statuses or timing can defeat generic wording. Globally observable service failure may be reported only without becoming an account-existence oracle. These are design implications; exact messages, status codes, throttle behavior and delivery retry rules remain decisions. [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-and-error-messages), [OWASP Forgot Password: analogous public request protections](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html#forgot-password-request)
