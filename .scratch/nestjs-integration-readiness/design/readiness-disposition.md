## Scope and concrete review scenarios

1. **Local independence:** local configuration remains usable with NestJS unavailable, including retained storage/save/conflict/recovery/export safeguards. Theme stays local. Later evidence must observe product network/state behavior, not infer independence from a mock passing.
2. **Permitted mixed increment:** real Authentication/account core can connect while Tasks/Projects/assignment/cascade remain local; editable connected Profile can follow. Local aggregate saves must not overwrite connected account/profile authority. This permits a configuration; it selects no first module or sequence.
3. **Coupled Workspace boundary:** when Workspace connects, real active-account authentication is required; Tasks, Projects, assignment, coherent reads and cascade share one authority. A connected error preserves approved feedback/draft/recovery behavior and never silently changes authority.
4. **Minimum frontend preparation:** use existing explicit operations where sufficient. Add only capability-justified authority separation, asynchronous states, validation/account isolation and test controls. No universal repository/adapter, preliminary form migration, cache, broad fixture framework or optimistic committed-update system is a prerequisite.
5. **Approved product refinements:** trace date-only due dates, server timestamp instants, null standalone project references, free-text assignee and display-name-only profile updates through their approved owners. They are connected contract requirements; this map changes no local code/storage.
6. **Implementation choices still due:** separate implementation planning selects justified persistence/transaction mechanisms, concrete interfaces, versions/build exports, provider/deployment/activation wiring and executable evidence controls. It must preserve approved same-origin cookie/password/CSRF and other API-visible guarantees; those are no longer unspecified mechanism choices. First real module integration revisits client tooling and actual browser/compiled-API compatibility.
7. **Evidence before activation:** use the testing strategy's capability-specific applicability matrix and record exact revisions/configurations, actual results and limitations. Prove required concurrency/durability/security at authoritative boundaries, browser behavior against the API and configured delivery for email-dependent activation. Guide readiness, historical passes and design approval cannot satisfy those observations.
8. **Scope boundaries:** no collaboration, offline synchronization, automatic failover/replay/dual writes, transition migration, email changes, password recovery, third-party identity, account deletion or global sign-out is introduced. Existing scoped enrollment recovery does not create active-account password recovery.
