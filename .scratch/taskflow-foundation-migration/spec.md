# Migrate TaskFlow to an independent React + NestJS foundation

Status: ready-for-agent

## Problem Statement

TaskFlow's frontend MVP was generated by Replit Agent from a single product prompt and committed to GitHub. The repository includes Replit-specific tooling, environment assumptions, platform restrictions, and generated infrastructure that make it harder to install, run, and maintain independently.

The maintainer needs a clean full-stack foundation without rewriting the original frontend. Preserving its implementation, UI, styling, state management, and behavior is the primary constraint. A migration that changes protected source, silently changes dependency behavior, or claims frontend equivalence without a baseline does not satisfy that need.

## Solution

Retain the existing React frontend unchanged inside a pnpm monorepo alongside a newly scaffolded NestJS backend. Remove unused generated infrastructure and operational dependencies on Replit, provide reproducible local commands and configuration, and validate fresh-checkout use on macOS and Linux.

The backend exposes only an infrastructure health endpoint. A configurable local proxy establishes the future API communication path without connecting the frontend application to the backend. Capture baseline evidence, verify source preservation and observable behavior, and deliver an evaluation guide that distinguishes automated results from pending human acceptance.

## Implementation Decisions

- Preserve all original frontend source, stylesheets, public assets, and the HTML entry file byte-for-byte. Relocation is allowed; formatting, import rewrites, component deletion, and frontend behavior fixes are not. Manifests, TypeScript configuration, Vite configuration, scripts, and project organization may change.
- Record the original revision and a complete protected-file inventory before migration. Account explicitly for the original-to-new path mapping when verifying preservation.
- Use a pnpm workspace with separately configured frontend and backend applications, individual application manifests, a single root lockfile, and root development/build/check entry points. The frontend remains React with its existing tooling; the backend is a standard Nest application. Do not add another monorepo orchestrator or speculative shared packages.
- Retain Node 24 and pin compatible Node and pnpm versions. Select a stable compatible NestJS version after checking runtime and scaffold-generator requirements. Resolve exact versions during implementation; do not upgrade frontend frameworks or tooling as a general cleanup activity.
- Preserve locked frontend direct and transitive dependency versions wherever compatible. Limit dependency changes to infrastructure removal, cross-platform installation, and the new backend. Review the lockfile and document unavoidable frontend resolution changes. Defer aggressive pruning of unused frontend dependencies.
- Audit references before removing the old health-only Express application, empty database scaffold, unused generated API client/Zod/OpenAPI pipeline, empty mockup sandbox, placeholder script package, and Replit runtime/tooling configuration. Remove obsolete workspace, build, script, and configuration references alongside the components. Preserve repository agent skills and guidance.
- Correct platform-specific native-dependency exclusions that prevent independent macOS/Linux installation. Review generated artifacts and installation hooks as infrastructure rather than assuming they are necessary to application behavior.
- Preserve incidental Replit comments and attribution inside protected files. Independence means removing operational reliance on Replit, not eliminating every textual mention. Keep existing Google Fonts requests; network access is permitted for installation and font loading.
- Default frontend local access to `http://localhost:21998/`, base path `/`, and backend local access to `http://localhost:8080`. Start without environment files or Replit-injected variables, bind locally, support documented port overrides, and fail clearly on occupied ports. Built preview may reuse the frontend port while development is stopped.
- Preserve SPA direct navigation and refresh in development and built preview. Preserve existing browser-local state behavior and storage key. Existing data remains tied to its browser origin; do not add data-transfer logic between origins.
- Expose only `GET /api/healthz`, returning HTTP 200 and JSON with a single `status` property equal to `ok`. The endpoint performs no database, authentication, or business checks.
- Establish `/api` as the future browser-facing API base. Configure Vite development and local built preview to forward API requests to the default backend, preserve request paths, and support a documented target override. API requests must not receive frontend SPA fallback. Do not add CORS for this same-origin approach.
- Keep communication preparation configuration-only: add no API clients, business endpoints, frontend data integration, or new application API calls. The health endpoint is used to exercise infrastructure externally. Document production routing as a future deployment decision.
- Capture baseline behavior before migration. If the original setup cannot execute unchanged, record the blocker and the exact configuration-only accommodation used. Do not alter protected source or claim unobserved behavioral equivalence.
- Document existing defects separately and defer fixes. If a protected-source defect prevents an agreed check from passing, surface the conflict explicitly rather than weakening the check or editing source.
- Add GitHub Actions coverage for macOS and Linux and document reproducible local workflows. Do not introduce linting or formatting requirements that force protected-source changes.
- Sequence the work as baseline capture, reference/deletion inventory, frontend relocation and infrastructure cleanup, backend/proxy scaffold, validation and review, then evidence-backed handoff. Exact command names, environment variable names, and compatible patch versions are implementation details within these constraints.

## Testing Decisions

- **Previously confirmed test boundaries:** Q12 established browser-visible frontend behavior, repository command behavior, and source preservation; Q11 and Q13 established the direct and proxied HTTP health boundary. The user confirmed these and the consolidated scope. No additional interview or seam approval is required for this synthesis.
- Prefer the highest observable boundaries: run the frontend as a user sees it, run the backend as an HTTP application, and exercise the repository through its documented commands. Avoid internal React state assertions, mocked controller/service tests, and tests that merely reproduce configuration structures. Source-byte comparison is a separate preservation invariant, not a replacement for behavior evaluation.
- **Prior art:** inspection found no installed dependencies, existing CI workflows, test scripts, or lint scripts. The old server already exposes the health contract, which is the existing external seam to preserve. There is no established test suite to claim as precedent; introduce only the minimal application-level smoke coverage needed for this foundation.
- Verify that protected files match the original revision byte-for-byte after relocation, with no omitted or deleted protected files. Review the frontend dependency graph and explain every unavoidable resolution change.
- Capture baseline browser observations, screenshots, console/network results, and existing defects. Use consistent browser version, viewport, device scale, timezone/date conditions, and stored data; wait for external fonts before visual comparisons. Preserve the evaluator's existing browser data by using a dedicated evaluation profile.
- Compare dashboard and navigation, project creation/editing/deletion, task creation/detail editing/deletion, board status movement, search and visible filters, settings/profile, demo login/signup, themes, desktop/mobile navigation and layout, validation and notifications, and persistence after refresh and same-origin restart. Include empty/no-match states and deletion cancellation/cascade behavior already provided by the frontend.
- Test direct application-route navigation and refresh, unknown frontend routes, and built preview. Record differences as baseline defects, migration regressions, or evidenced environmental differences. If baseline execution is blocked, behavioral acceptance remains unverified.
- From fresh checkouts on both macOS and Linux, run frozen-lockfile installation, typechecking, builds, and the backend smoke test using pinned versions. Record each platform separately and supply GitHub Actions evidence. One platform's success does not establish the other's.
- The backend smoke test must boot the actual Nest application, issue an HTTP request, assert the health status and JSON contract, and close cleanly. It must not require a database or frontend process.
- Verify independent frontend/backend startup, no-environment-file defaults, documented port overrides, and clear occupied-port failure. Keep frontend navigation usable when the backend is stopped.
- In both frontend development and local built preview, request the proxied health endpoint and verify HTTP 200 and the exact agreed JSON content. Repeat with an alternate backend port and proxy target override. Confirm an unknown API request reaches the backend rather than returning frontend HTML. With the backend stopped, explicitly requested proxied calls must fail visibly.
- Inspect ordinary frontend browser activity to confirm no new application API calls. Review the final diff for protected-source changes, business endpoints, clients, accidental integrations, obsolete infrastructure references, and operational Replit dependencies.
- Complete a feature-by-feature evaluation guide with exact commands, versions, fixture/setup details, evidence locations, platform results, baseline defects, and outstanding failures. Give the user the first concrete startup/evaluation action. Automated passes and guide readiness do not establish human acceptance; keep it pending until the user reports observations.

## Out of Scope

- Frontend refactoring, formatting, import rewrites, design changes, behavior changes, unused-component deletion, or fixes to existing protected-source defects.
- Business logic, business endpoints, database persistence, ORM/schema work, authentication, API clients, generated contracts, or actual frontend-backend data integration.
- General frontend dependency upgrades, aggressive unused-dependency pruning, new monorepo orchestration frameworks, or speculative shared packages.
- Direct cross-origin communication/CORS configuration, production API routing, hosting, deployment infrastructure, containers, or production publication.
- Windows acceptance, full offline operation, font self-hosting, browser data transfer between origins, and removal of Replit attribution from protected files.
- Removing repository agent skills or guidance, rewriting Git history, or treating this spec publication as authorization to begin implementation.
